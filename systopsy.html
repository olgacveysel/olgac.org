Systopsy · Coming next

An autopsy for crashed servers.

Point Systopsy at a host that went down. It collects the evidence, rebuilds the timeline and tells you what killed it, in plain language with the log lines to prove it.

Request early access Source goes public at beta

The problem

When a production server crashes, the cause is almost always written down somewhere: the kernel ring buffer, journald, a service's error log, the OOM killer report. But it's spread across many files and timestamps, and the engineer reading it is under pressure. The first part of every incident is the same tedious grep-and-correlate work.

The approach

Systopsy automates that first part. A local collector gathers evidence and builds one ordered timeline. A rule engine flags well-known failure patterns. Then, if you choose, an AI model reasons over the reduced, redacted evidence and writes a ranked root-cause report with cited lines and concrete fixes.

systopsy
$ systopsy collect --since "2h ago"
✓ kern.log  ✓ journal  ✓ dmesg
✓ app logs  ✓ metrics  (3 secrets redacted)

$ systopsy analyze --ai none
rule OOM_KILL       mysqld  HIT
rule DISK_FULL      /var    ok
rule KERNEL_PANIC   -       ok
› exported evidence.md + prompt.txt

$ systopsy analyze --ai local
› model running on this machine
› nothing sent over the network
✓ report written to report.md

What it understands

Linux & kernel

OOM kills, kernel panics, hung tasks, segfaults and filesystem errors.

Services & databases

Failed systemd units, crash loops, database crashes and recovery, memory misconfiguration.

Resources

Memory, disk and I/O exhaustion, runaway processes and full filesystems.
